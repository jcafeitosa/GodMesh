## 1. Tabela de ACK normativa (ADR-058)

Classes aprovadas em `decisoes.md:144`: conjunto fechado `transport_accepted`, `persisted_local`, `replicated_to_authority`, `materialized`, `delivered_to_device`, `acknowledged_human`; toda resposta de API deve carregar `ack_class`; é proibido usar "ACK" sem classe e proibido inferir classe superior por tempo, por sucesso de camada inferior ou por ausência de erro. **Estado atual: `ack_class` foi incorporado às SPECs em 17/11/2026; presença textual verificada, implementação não** — a aplicação nos textos é o item 3 da ordem de execução em `docs/09-equipe/registro-gaps.md:113` (pendente). ## 3. Confidencialidade herdada (ADR-060)

Regra única, derivada de ADR-060 (`decisoes.md:166`) e registrada aqui porque atravessa todos os contratos deste índice:

1. **Herança obrigatória.** Todo derivado de conteúdo — transcrição, gravação, projeção de timeline, snapshot de SOS e payload em bridge, sem lista fechada — herda `confidentiality=terminated` quando **qualquer** perna da cadeia termina a proteção. Basta uma perna terminadora: bridge, ASR no servidor com consentimento, gravação, exportação. Não existe derivado "mais protegido" que a perna que o produziu.
2. **Falha fechada por metadado ausente.** Se o metadado de confidencialidade faltar, estiver ausente na cópia, ou não for verificável, o consumidor trata o artefato como `confidentiality=terminated`. Ausência nunca significa E2EE, nem é suprida por inferência, cache, versão anterior ou ausência de erro.
3. **Proibição de alegação.** A API **rejeita** alegação de E2EE sobre qualquer artefato terminado ou sem metadado; TLS/DTLS/SRTP não sustentam alegação de E2EE (`decisoes.md:166`). UI e API exibem `terminated` de forma visível.
4. **Escopo desta seção.** Ela registra a regra normativa e o comportamento exigido; não define enum, nome de campo wire, perfil por operação nem criptografia. O campo `confidentiality` segue inexistente em `docs/07-contratos/` e em SPEC — divergência D9, ainda aberta.
